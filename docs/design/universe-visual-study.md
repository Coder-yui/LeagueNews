# League of Legends Universe Visual Study

> 研究对象：Riot Games 的 League of Legends Universe 官网（以英文站首页、地区索引、地区详情、英雄详情、故事阅读与漫画内容中心为主要样本）
>
> 研究时间：2026-08-13
>
> 文档目的：提炼可用于现代 League of Legends 资讯产品的视觉设计原则，而非复制 Universe 的页面或品牌资产
>
> 本阶段边界：仅做研究与原则总结；不包含 LeagueNews 改造方案、组件定义或实现建议

## 1. Executive Summary

Universe 的核心视觉机制不是“黑底、金色、游戏字体”，而是把一个内容目录塑造成一座**可进入、可探索、彼此关联的世界档案馆**。

它通过五组相互配合的机制建立这种体验：

1. **图像提供地点与情绪，UI 提供秩序。** 大幅环境图让用户先感知“这是哪里、气氛如何”，低饱和的结构层、细边框和标题系统再帮助用户理解内容。
2. **编辑策展替代均质信息流。** Featured、地区、角色、故事和相关内容不是同尺寸卡片的无限列表，而是通过尺度、位置、图文关系和上下文连接形成阅读路径。
3. **层次依赖明度、比例和空间，而不依赖容器堆叠。** 页面只有少量真正突出的暖白与金色，大多数背景、边框和辅助文字都主动后退。
4. **装饰承担语义与节奏。** 细线、菱形、徽记、框线和大写小标题用于宣告章节、归属和可交互性，而不是覆盖在每个元素上充当“游戏感”。
5. **克制的仪式感包围可读内容。** Display 字体、居中标题与入场动效负责建立气氛；正文、元数据与浏览列表则回到稳定、清晰、可扫描的排版。

对 LeagueNews 最有价值的启示，是把“新闻条目”提升为有主次、有出处、有事件上下文的编辑对象，同时保留高频资讯产品需要的扫描效率。应学习 Universe 的**层级控制、图像整合、空间节奏与关联叙事**，而不是复制其专属字体、地区徽记、纹样或沉浸式 Lore 阅读节奏。

## 2. Visual Identity

### 2.1 整体气质：权威档案、史诗画册与探索界面的交集

Universe 同时具有三种气质：

- **档案馆的权威感**：统一的分类、明确的内容归属、克制的框线与规整的标题，让内容像被正式收录，而非临时发布。
- **画册的观赏性**：图像通常有足够面积，并被允许成为页面主角；文字不会把图片切成无数小缩略图。
- **探索界面的方向感**：地区、角色、地图、相关故事之间持续互链，用户面对的不是一篇孤立内容，而是进入下一层世界的入口。

这使它看起来不像普通 SaaS 或新闻网站。SaaS 常把信息装进可复用面板，以圆角、阴影、状态色表达层级；一般新闻网站常把时效、栏目与标题压缩为高密度列表。Universe 则把页面看成一个连续舞台：背景、图像、文字和框架共同占据同一空间，组件边界往往弱于场景边界。

### 2.2 世界观如何建立

世界观不是由一句介绍建立，而由以下链条持续累积：

`地点/角色图像 → 专有徽记与命名 → 简短背景说明 → 相关角色/故事 → 下一处可探索内容`

其中最重要的是**关系被可视化**。地区页不只介绍地区，还显示居住于此的角色和相关故事；角色页通过种族、职责、地区、相关角色和传记把人物嵌入世界；故事读完仍能继续发现关联内容。用户因而不断获得“这个内容在世界中的位置”。

### 2.3 内容与背景的关系

Universe 很少让背景只是未参与布局的壁纸。背景通常承担以下一种或多种任务：

- 在 Hero 中定义地点、人物或故事的第一印象；
- 以极低透明度延续到内容区，使页面不在 Hero 结束后突然失去世界感；
- 通过暗角与方向性渐变为文字制造可读区域；
- 在 Section 切换时改变色温或纹理，提示叙事阶段变化；
- 让边框与内容面板像浮在场景中的“档案层”，而不是独立的白色/灰色卡片。

因此背景与内容不是“装饰 + 前景”的简单二层关系，而是**气氛层、结构层、内容层、强调层**的连续深度关系。

### 2.4 品牌感来自哪里

真正可学习的设计语言：

- 大幅场景与紧凑信息之间的节奏切换；
- 明确而稀少的视觉强调；
- 编辑式的大标题、章节标题与关联内容；
- 低对比框架把内容组织成档案或展陈；
- 图像色调与 UI 色阶的主动融合；
- 几何装饰的系统化重复；
- 内容之间持续呈现地点、人物、故事的关系。

主要由 Riot 高质量美术资源带来的效果：

- 角色辨识度、世界地点的完整概念设计；
- 每个地区独有且成熟的色彩、纹理、建筑与符号体系；
- 可直接承担 Hero 的电影级插画与 Key Art；
- 官方徽记、武器、服装、材质与叙事细节所带来的真实性；
- 同一 IP 内图像资产天然一致的艺术指导。

如果拿走 Riot 插画，Universe 的结构仍然成立：强弱分明的标题、有限宽度、低对比框架、章节节奏、关联发现和克制动效仍能产生“策展式内容体验”。但它不会自动产生 Runeterra 的具体世界感。这一区分是后续设计的底线。

## 3. Typography

### 3.1 字体角色分工

Universe 的生产样式显示出清晰的角色分配：

- **Beaufort for LOL（Display Serif）**：页面标题、卡片标题、地区/角色名、导航中的品牌级栏目、按钮与小型仪式化标签。其作用不是单纯“复古”，而是提供碑铭、典籍与史诗标题的语气。
- **Spiegel（UI Sans）**：说明文字、列表副标题、界面信息、较小的功能性文本。它降低 Display 字体连续出现造成的视觉噪声。
- **传统阅读 Serif（故事正文中使用 Times New Roman / Georgia 类角色）**：长篇故事正文。生产样式中桌面正文约 20–21px、行高约 1.58–1.75、内容宽度约 700px，说明长读模式与浏览/UI 模式是分开的。
- **特定专题字体**：Alt Universe 或活动页可以有局部替换，但它们属于专题主题，不是全站基础语言。

核心不是使用哪一个具体字体，而是建立三种语气：**宣告、操作、阅读**。同一字体承担全部角色，会让页面要么过于平淡，要么持续处于“喊叫”状态。

### 3.2 典型层级

以下是对 Universe 实际样式与页面样本的抽象，不是 LeagueNews 的实现数值：

| 层级 | 典型用途 | Universe 的处理 | 可迁移原则 |
| --- | --- | --- | --- |
| Display XL | 故事、地区、角色首屏标题 | Serif Display，桌面可达约 60–95px，大写，紧行高，较大字距 | 只给页面唯一主命题；短而有力 |
| Display L | Feature / Section 主标题 | 约 32–60px，中等或粗字重，暖白 | 用尺度而非亮色夺取第一注意力 |
| Heading M | 卡片、内容组标题 | 约 18–24px，常大写，约 `.05em` 或 2–3px 字距 | 保持短句，避免一整段全大写 |
| Eyebrow / Label | 类型、章节、归属、动作提示 | 约 11–14px，大写，1–4px 字距，暗金/次级白 | 作为导航标记，不与主标题竞争 |
| UI / Metadata | 作者、地区、分类、时间等 | Sans，约 12–16px，常用低对比色 | 信息要可扫读，避免装饰性字体 |
| Long-form Body | 故事正文 | 阅读 Serif，约 18–21px，行高 1.58–1.75，窄栏 | 长读优先舒适度，不延续 Hero 的戏剧性 |
| Browse Body | 摘要、说明 | Sans 或较平静的 Serif，约 14–18px，行高 1.4–1.6 | 摘要比标题安静，比元数据清晰 |

### 3.3 大写、字距与字重

- 大写主要用于**短标题、栏目名、标签、按钮和导航**，用于创造铭牌感和清晰轮廓。
- 字距随文字变小而增大：大标题已经有足够形态，不需无限拉开；小标签需要 1–4px 或约 `.05em–.3em` 的间距形成仪式感。
- Display 常用 500/700，但并不依赖极黑字重。气势更多来自字号、全大写、留白与对比。
- 正文避免高字重；辅助信息以降低明度而非过度缩小来后退。
- 连续多行全大写不适合中文，也会损害英文新闻标题的阅读速度。迁移时应保留“短标签大写”，不保留“所有内容大写”。

### 3.4 居中与左对齐

**居中**出现在需要宣告、停顿或建立仪式感的位置：首屏标题、故事标题/作者、章节开场、少量关键引语、内容组的独立开场。

**左对齐**出现在需要扫描、比较或连续阅读的位置：卡片列表、说明段落、长篇正文、元数据组合、内容索引。

判断原则：居中回答“我现在进入了什么”；左对齐回答“我接下来要读什么、比较什么”。高频新闻界面应把居中限制在页面/栏目级，不应让每张普通卡片都居中。

### 3.5 可迁移 Typography 原则

1. 建立 Display、UI、Reading 三种明确文字角色，而非先选“LOL 风字体”。
2. 页面只允许一个 Display XL；普通内容不要共享 Hero 的音量。
3. 通过“字号 + 空间 + 明度”建立标题权重，金色只做归属或强调。
4. 大写与宽字距只用于短文本；中文通过字重、字号和留白实现同等层级，不机械增加字距。
5. 元数据必须稳定、易扫描，不使用装饰字体，不与类别标签混成同一视觉重量。
6. 长篇阅读切换到窄栏、舒适行高和较平静字形；氛围不能以牺牲可读性为代价。
7. 居中用于入口与章节，左对齐用于内容消费与判断。

## 4. Color

### 4.1 不是纯黑，而是有色温的暗部体系

Universe 的基础暗色包含多组接近但功能不同的层次，例如生产样式中的 `#0a0a0c`、`#010a13`、`#111315`、`#131415`、`#1a1d21`。它们可抽象为：

| 功能层 | 色彩倾向 | 作用 |
| --- | --- | --- |
| Canvas | 近黑、略偏蓝或中性 | 消除网页白底感，承接全局气氛 |
| Deep Field | 蓝黑/墨蓝 | 与夜色、地图、环境图融合，产生深度 |
| Surface | 比 Canvas 略亮的煤黑 | 承载文本与结构，不显得像悬浮 SaaS 卡片 |
| Raised / Hover | 再提高一小级明度 | 表示响应和焦点，不依赖强阴影 |
| Scrim | 半透明黑 | 控制图片亮度、保障文字可读性 |

这些层次的差值很小，因此用户首先感知的是一个连续暗环境，其次才感知容器。

### 4.2 文字与强调色的功能关系

| 角色 | 典型倾向 | 使用逻辑 |
| --- | --- | --- |
| Primary text | 暖白/羊皮纸白（如 `#f0e6d2` 一类） | 主标题与关键内容；比纯白更能与金色、插画共存 |
| Secondary text | 灰米色/冷灰（如 `#c4b998`、`#a09b8c` 一类） | 摘要、说明、次级标题 |
| Muted text | 降低明度和不透明度的灰金/灰蓝 | 元数据、非当前项、辅助说明 |
| Accent | 旧金、黄铜、暗金（如 `#937341`、`#c8aa6e` 一类） | 归属、徽记、细线、短标签、选择状态 |
| Structural line | 金灰色低透明度（常见约 20%–37%） | 框架、分隔、轮廓；被看见但不被首先注意 |
| Interactive high accent | 少量更亮的蓝/青 | 全局“Play Now”等强行动，不是内容页的主色逻辑 |

金色在系统中更接近**标点和索引色**，不是大面积填充色。若把所有按钮、边框、标题和图标都变成金色，就会摧毁它原本制造层级的能力。

### 4.3 图片与 UI 如何融合

Universe 常用以下组合，而不是给图片单独加一个统一滤镜：

- 黑色或蓝黑的半透明 Scrim 压低整体亮度；
- 底部深色渐变为叠加标题和摘要建立稳定落点；
- 方向性渐变在文字所在一侧更深、主体所在一侧更透明；
- 暗角让画面边缘与页面 Canvas 融合；
- 非焦点内容降低亮度、饱和度或转为灰度；
- UI 线条取自图片中已存在的暖色/金属色，而非在画面上强行增加新色；
- 专题页可以改变主题色，但基础明度关系保持一致。

### 4.4 渐变、光晕与 Overlay 的作用

- **渐变**主要解决可读性和空间融合，不应只是视觉特效。
- **暗角**控制视线中心，并把宽屏图片的边缘收回页面。
- **低透明背景图**给长页面连续性，但不允许影响正文对比。
- **光晕/阴影**通常较软、较大，用于把特殊对象从深色环境中分离；普通卡片不靠明显投影悬浮。
- **边框渐变**偶尔用于按钮或圆形徽记，表达材质层次；大多数结构线仍保持单薄。

### 4.5 色彩原则

不要先定义“品牌黑、品牌金”，而应先定义功能关系：

`环境暗部 < 结构表面 < 悬停/当前表面 < 次级文字 < 主要文字`

以及：

`结构金 < 标签金 < 交互/关键强调金`

同一色相必须有至少三档权重，才能让页面既有品牌感又不遍地高亮。状态色（可信度、风险、成功等）属于产品语义，应独立于品牌金，不可用金色覆盖所有含义。

## 5. Layout & Spacing

### 5.1 Hero：先建立语境，再交付内容

Universe 的 Hero 常见两种模式：

1. **沉浸式中心构图**：全宽或接近全宽图像，标题、作者/副标题居中，适合故事、角色或世界入口。
2. **编辑式分栏构图**：大图占约 60%–65%，说明占约 35%–40%，适合 Featured 或专题介绍。生产样式中可见 65/35 的 Feature 分配。

Hero 的共同目标不是展示尽可能多的信息，而是在首屏回答：

- 这是什么内容；
- 它属于什么世界/地区/类型；
- 我为什么值得继续向下；
- 下一步动作是什么。

Hero 下方通常有明确的结构转换，例如标题面板压住图像边缘、细线收口、引导滚动，或进入较窄的内容栏。这种“场景 → 内容”的转换非常关键。

### 5.2 最大宽度与多层容器

生产样式反复出现约 1100–1280px 的主内容上限，长文正文约 640–700px，部分内容泳道约 1200px / 85vw。这体现出多层宽度，而不是全站一个 `max-width`：

- **Atmosphere width**：接近视口宽度，用于 Hero、地图、背景和大型画面；
- **Editorial width**：约 1100–1280px，用于内容组、Feature、地区/漫画网格；
- **Reading width**：约 640–700px，用于长段正文；
- **Annotation width**：更窄，用于摘要、引语和局部说明。

宽度变化本身就是信息层级。主内容越重要，未必越宽；长文反而主动收窄以提升专注与可读性。

### 5.3 留白与节奏

Universe 在内容很多时仍不拥挤，原因不是简单“大留白”，而是留白有明确层级：

- Hero 与第一个内容 Section 之间有一次明显停顿；
- Section 间距显著大于卡片间距；
- Section 标题与内容之间保留一段可感知的空白，并常以细线延伸；
- 卡片内部留白少于卡片外部的分组留白；
- 同一组卡片密度稳定，不在每张卡上塞入不同数量的徽章；
- 重要内容通过占据更大面积获得权重，而不是在同一密度中提高颜色噪声。

可抽象为比例：若普通内容间距为 1，卡片组间距约 2，Section 间距约 4–6，页面阶段切换可达到 6–8。具体数值可变，但比例必须明显。

### 5.4 大图与文字关系

- 叠加文字只放在已通过渐变建立可读区的图像上；
- 当文字解释较长时，图文分栏，不强迫所有文字压在图上；
- 图像主体决定裁剪与文字方向，布局服从美术焦点，而不是固定“永远左文右图”；
- 普通内容列表的图像比例稳定，Feature 可以突破比例；
- 图片承担情绪和辨识，正文承担事实与细节，两者不互相重复。

### 5.5 桌面与移动端变化

Universe 的样式以约 767px 和 1024px 为主要结构变化点。移动端不是单纯缩小：

- 65/35 分栏改为纵向堆叠；
- 大标题从约 60–95px 降至约 30–42px，并减少字距；
- 桌面侧向翻页按钮常隐藏，改由触摸横向浏览或更直接的纵向流；
- 桌面装饰框在窄屏上隐藏或只保留上下边界；
- 内容宽度改为约 90%–98%，但阅读正文保留内边距；
- 背景图从绝对定位场景改为上方独立图像，并用底部渐变接入正文；
- 一些说明性副标签被隐藏，避免移动首屏过载；
- 卡片组从多列变单列或横向泳道，仍保留清晰分组。

移动端迁移原则：保留信息顺序和对比，删除不再有空间价值的装饰与并列关系。不能把桌面端所有框线、徽记、标签等比例压进手机。

## 6. Cards & Content Presentation

### 6.1 Featured 内容

Featured 通常不是“普通卡片加一个 Featured Badge”，而是在四个维度上同时升级：

- **面积**：拥有最大的画面或最宽的跨列占位；
- **位置**：出现在页面开场或内容组第一位；
- **图文关系**：允许独立说明面板、文字压图或中央标题牌；
- **上下文**：提供一句能够解释“为何重要”的副标题或引导。

Featured 的权重来自整体构图，不来自更多元数据。它通常反而比普通信息卡更安静、更少标签。

### 6.2 普通图片卡片

地区索引、漫画列表和关联故事体现了三类处理：

- **图上标识 + 图下标题带**：地区卡用氛围图和徽记建立识别，名称在稳定暗色底栏中保证扫描。
- **整图 + 底部渐变 + 叠加文字**：适合故事、漫画或内容泳道；标题靠左落在一致位置。
- **图文分栏/横向卡**：适合摘要更长、需要同时显示来源与描述的内容。

卡片的共同特征是：图像占据大部分面积，文本数量受控，边界薄而直，圆角很少或接近没有，阴影不是主要层级工具。

### 6.3 横向内容与内容泳道

Universe 使用横向泳道展示同类内容，尤其适合“最近添加”“相关故事”“角色”。它的价值在于：

- 保持卡片足够大，不为塞进一屏而缩成缩略图；
- 让 Section 本身成为一组清晰的内容语义；
- 用方向按钮和部分露出提示仍有更多内容；
- 在移动端自然转为横向滑动，避免超长单列。

对高频新闻产品而言，横向泳道应只用于精选或专题发现，不适合作为核心时序信息流，因为隐藏的横向内容降低可见性与比较效率。

### 6.4 标题、分类与元数据

- 分类标签通常短、小、大写、暗金或次级色，位于标题上方或图片底部；
- 标题使用 Display，暖白，控制在 1–3 行；
- 副标题/摘要使用 Sans 或平静正文色，限制长度；
- 作者、地区、类型等 Metadata 不同时争夺注意力；
- “Explore / Read” 更像文字动作或细框按钮，不是高饱和彩色胶囊。

### 6.5 Hover 状态

观察到的典型行为包括：

- 图片约 1.05 的轻微放大；
- 边框、标题或箭头从暗金升到暖白/亮金；
- 圆形角色图外环轻微放大；
- 非焦点图像降低亮度或转灰，动作文字显现；
- 表面明度提高一个层级；
- 动画常在 0.2–0.5 秒之间，图片淡入可稍慢至约 0.8 秒。

Hover 不是给卡片增加大幅位移或强发光，而是确认“此处可进入”，并把焦点从画面转向动作。

### 6.6 与普通 SaaS Card 的区别

| 普通 SaaS Card | Universe 内容单元 |
| --- | --- |
| 圆角容器是组件身份 | 图像、标题带和框架共同定义内容身份 |
| 阴影表现层级 | 尺度、位置、明度和图像权重表现层级 |
| 每张卡结构高度标准化 | 同一内容等级内一致，Featured 可有编辑式破格 |
| Badge 和图标传递状态 | 少量标签传递类型，主体意义由标题/图像承担 |
| 白/浅表面与页面分离 | 暗表面与页面环境连续融合 |
| Hover 常整体上浮 | Hover 多为图像、边框、色彩和动作提示的局部变化 |

### 6.7 卡片原则

卡片可以没有圆角、明显阴影甚至完整包围框；但不能没有：

- 稳定的图像比例或文字落点；
- 清晰的标题与类型关系；
- 内容级别一致的内外间距；
- 可预期的交互反馈；
- 与背景足够但不过强的边界；
- 对缺图内容同样成立的文字层级。

## 7. Decorative Elements

### 7.1 元素词汇

Universe 反复使用的装饰语言包括：

- 1px 低对比金灰细线；
- 细线起点或交汇处的小菱形；
- 圆形角色头像与双层细环；
- 地区/类型徽记；
- 内容外侧的大型细框；
- 局部角标、短横线、箭头；
- 小型大写标题和加宽字距；
- 极低透明度的纹理、徽记或背景人物；
- 顶边、底边或图文交界处的窄金属色边线。

### 7.2 它们为什么有效

这些元素不是随机“奇幻装饰”，而有四种功能：

1. **分组**：长细线把 Section 标题和后续内容连接起来。
2. **归属**：徽记快速表示地区、角色或内容类型。
3. **焦点**：菱形、短横和角标给视线一个精确落点。
4. **仪式**：边框和对称构图让某些入口像正式开启一份档案或章节。

### 7.3 使用纪律

应建立“装饰预算”：

- 每个 Section 最多一个主要 ornament motif；
- 装饰只出现在层级转换、归属表达或关键动作附近；
- 普通重复列表不为每个元数据加框；
- 细线保持低对比，亮金只给活动状态或关键焦点；
- 角饰不同时出现在卡片、按钮、标签和图片四个层级；
- 徽记必须有真实分类含义，不能只是填空；
- 若拿掉装饰后信息结构无法理解，说明结构本身不够清楚；若装饰比内容先被看到，说明使用过量。

### 7.4 如何避免廉价“游戏 UI”

廉价感通常来自把表面符号当作品牌机制：所有容器都有切角、所有按钮发光、所有标题金色、所有边角有花纹。Universe 实际上把复杂纹样主要留给美术和少数高层入口，基础 UI 更接近严谨的编辑框架。

正确做法是：**复杂内容配简单框架，简单入口才允许少量仪式化装饰**。装饰的密度应与信息密度反向变化。

## 8. Image Treatment

### 8.1 图片比例与等级

- Hero 使用宽幅电影比例或高占屏场景，目的在于建立语境；
- Featured 允许约 16:9、宽幅或 65/35 图文组合；
- 普通故事/漫画卡多使用稳定的横幅或竖幅系列比例；
- 地区索引使用一致横向图窗，上方环境图、下方名称带；
- 角色头像使用圆形裁剪，是“身份对象”而不是新闻缩略图；
- 长文插图可以突破正文宽度，但正文仍保持窄栏。

图像比例不是美化参数，而是内容类型信号。不同内容类型可有不同固定比例，同类型不可频繁变化。

### 8.2 裁剪方式

- 普通卡片以 cover 为主，保持固定框架；
- Hero 按人物脸部、动作方向或地平线重新选择焦点；
- 移动端常改变 background-position，必要时把背景图转为独立图块；
- 文字侧要有负空间或可被 Overlay 安全压暗的区域；
- 不应为了维持固定左右布局而切掉主体。

### 8.3 Brightness / Saturation / Contrast

Universe 的截图与样式显示，图片在 UI 中通常比原画更暗：

- 亮度被压低，尤其是边缘和文字所在区域；
- 饱和度没有统一归零，而是让内容主题色仍可识别；
- 暗部对比维持，以免图像变成灰雾；
- 非当前/旁侧项目可转灰或显著降亮；
- 当前焦点恢复颜色与明度，形成无需额外描边的选择状态。

目标不是“所有图片套暗色滤镜”，而是把各来源图像校准到共同的**UI 明度范围**。

### 8.4 Overlay 与文本叠加

文本叠图需要同时满足：

- 有稳定的深色落点，而非依赖某一张图碰巧较暗；
- 主体与文字不重叠；
- 渐变方向服从文字位置；
- 标题之外的正文数量受控；
- 在图片加载失败或无图时仍有可理解的内容结构。

大图 Overlay 可以更富戏剧性；缩略图应使用可预测的底部渐变和固定文字区域，避免每张卡都成为一张海报。

### 8.5 Hover Zoom

约 1.03–1.05 的慢速放大足以表达可探索性。必须在裁剪容器内发生，且不能改变卡片尺寸或导致列表跳动。高频内容流不应对每次鼠标经过都执行强烈变焦、模糊或全卡位移。

### 8.6 无高质量专属插画时仍成立的策略

- 优先使用来源本身可靠、清晰、与内容直接相关的媒体；
- 通过统一裁剪、明度校准和 Overlay 建立一致性；
- 缺图时使用排版型内容单元，不用廉价通用幻想背景补位；
- 让栏目、事件和来源关系承担辨识，不让图片独自承担全部品牌；
- 不伪造“Riot 官方感”，不把非官方素材处理成看似官方 Key Art。

## 9. Motion & Interaction

### 9.1 Universe 中的动效类型

- 首次加载与 Section 进入时的淡入、轻微上移；
- 图片加载后约 0.4–0.8 秒的显现；
- 导航/Modal 以顶部为原点展开；
- Hover 时图片轻微放大、外环放大、颜色/灰度切换；
- 箭头与动作文字的淡入或水平移动；
- Carousel / 泳道切换；
- 故事页的滚动引导、章节感和阅读进度；
- 地图中的镜头移动、地标动画与空间探索。

### 9.2 真正增强体验的动效

- **焦点确认**：Hover 时局部增亮或显现动作，帮助理解可点击区域；
- **层级过渡**：Hero 到正文、Modal 打开、Section 入场时的短过渡，帮助用户理解空间变化；
- **方向提示**：Carousel 箭头、部分露出的下一张、轻微平移提示还有内容；
- **阅读定位**：章节/进度反馈帮助长内容理解当前位置；
- **世界空间化**：地图镜头与地标动画直接服务“地点关系”，不是装饰。

### 9.3 LeagueNews 应谨慎或避免的动效

- 每个普通消息卡的滚动入场动画；
- 自动轮播 Featured，尤其会在阅读中更换内容；
- 长时间 Preloader、页面转场或必须等待的揭幕；
- 大范围视差、背景持续漂移、粒子和环境视频；
- Hover 后隐藏原有信息、强制用户再次寻找动作；
- 对时序列表使用大幅缩放、翻牌或复杂 3D；
- 使实时更新造成布局跳动或重复闪烁；
- 把重要性、可信度、热度变成持续脉冲的“战斗 HUD”。

### 9.4 动效原则

高频资讯中的动效应服务三件事：**反馈、定位、状态变化**。氛围动效只能出现在少量低频入口，不能增加读取最新信息的时间成本。所有关键状态都必须在静止画面中成立，并尊重 reduced-motion 偏好。

## 10. Information Hierarchy

### 10.1 Universe 如何告诉用户什么最重要

Universe 使用一组叠加信号，而不是单一“重要”标签：

1. **位置**：最重要内容出现在首屏或 Section 首位；
2. **面积**：更大的图像与标题占位；
3. **对比**：暖白标题、完整彩色图片，周边内容更暗；
4. **独占空间**：Feature 周围留白更多，不与多个徽章争夺；
5. **上下文文案**：一句副标题说明内容的意义；
6. **入口强度**：更明确的 Read / Explore 动作；
7. **关联数量**：后续出现相关角色、地区与故事，证明其在世界中的位置。

Featured 因此是一个**编辑决策**，不是一个布尔样式。

### 10.2 分类、标题与 Metadata 的层级

典型阅读顺序为：

`画面/场景 → 类型或归属 → 标题 → 一句解释 → 动作 → 辅助 Metadata`

分类通过小型大写标签、徽记或 Section 名表达；标题占据主要文字对比；Metadata 则降低明度、字号或改用 Sans。Universe 不让日期、作者、地区、媒体类型全部变成彩色胶囊，因此用户不会先读到一排系统字段。

### 10.3 可应用于新闻产品的层级规则

对 LeagueNews 已有的消息、事件、日报、信源与评分语义，可以抽象出以下规则（仅为信息层级原则，不是页面方案）：

1. **先表达新闻价值，再表达系统字段。** 用户首先需要标题、当前事实/摘要和为何值得关注；ID、处理状态与结构化类型不能排在它们之前。
2. **“消息”与“事件”必须有不同视觉语法。** 消息是一次发布；事件是跨来源、随进展更新的当前结论。不能只改一个标签而复用完全相同的权重结构。
3. **Featured 必须同时改变位置、尺度和上下文。** 仅增加金色边框或“精选”Badge 不足以建立真正优先级。
4. **重要性、可信度、热度保持独立。** 三者是不同判断轴，不应压缩成一个综合颜色或共同高亮；品牌色也不应替代这些产品语义。
5. **来源是信任证据，不是装饰标签。** 在快速扫描层只显示必要的来源信息；需要核验时再展开完整证据和原始链接。
6. **Metadata 采用渐进披露。** 列表只保留影响选择的字段，详情提供证据、时间线、修订和结构化结果。
7. **同层内容保持稳定模板。** 标题落点、摘要长度、图片比例和元数据顺序一致，用户才能快速比较。
8. **缺图不等于低重要性。** 信息权重不得完全依赖媒体资产；排版型 Feature 与无图事件必须能够成立。
9. **最新不等于最重要。** 时序决定浏览顺序之一，编辑优先级需要独立的面积、位置或栏目表达。
10. **进展优先于重复报道。** 事件视图应把“最新实质进展”放在来源数量之前，数量是佐证而非主叙事。
11. **栏目是阅读承诺。** 日报、消息流、事件流应明确告诉用户各自回答的问题，不要只表现为三个同形列表。
12. **每个视图只有一个第一注意点。** 若 Hero、统计、Lead Story、多个彩色评分同时高亮，就等于没有层级。

### 10.4 新闻层级的四层模型

| 层级 | 用户问题 | 应承担的信息 |
| --- | --- | --- |
| L1 · Orientation | 我在看什么？ | 页面/栏目命题、日期或时间范围、筛选语境 |
| L2 · Editorial Priority | 先看什么？ | Feature、重大进展、日报头条、清晰的重要性理由 |
| L3 · Scan & Compare | 还有什么？ | 稳定列表中的标题、摘要、时间、来源、必要指标 |
| L4 · Evidence & Depth | 为什么可信？发生了什么变化？ | 原文、证据、事件时间线、来源角色、修订、结构化细节 |

Universe 的可迁移价值，在于让 L1–L4 有明显的空间与视觉区别，而不是把所有字段平铺在每张卡上。

## 11. What Makes Universe Feel Like Universe

以下因素比“深色 + 金色”更接近其真正机制：

1. **内容被放进一个有地点关系的世界，而不是一个无上下文的 CMS。** 地区、人物、故事和地图持续互相解释。
2. **每个页面先建立“进入感”，再进入浏览或阅读。** Hero、标题、图像与下行过渡共同完成心理换场。
3. **图像不是卡片附件，而是空间和语气的来源。** UI 的暗部、渐变和强调色反过来适应图像。
4. **编辑策展制造层级。** Featured 通过面积、位置、独占空间和说明被真正提升，而不是贴一个标签。
5. **Display 与功能排版有明确分工。** 史诗感集中在标题与入口，阅读和操作层保持克制。
6. **暗色层次连续而有深度。** Canvas、Surface、Scrim 和图片暗部彼此接近，使页面像一个环境而非卡片墙。
7. **装饰是语法，不是贴纸。** 细线、菱形、徽记和框架在分组、归属、焦点与仪式之间各有职责。
8. **内容之间总有“下一步关系”。** 相关人物、地区、故事和媒体使发现路径不断延续，减少死端。
9. **安静区域让戏剧性成立。** 大量低对比内容和留白衬托少数高对比画面与标题；如果处处史诗，就没有史诗。
10. **主题可变，但骨架稳定。** 不同地区/Alt Universe 可以改变色彩与美术语气，分类、排版角色、交互和可读性规则仍保持一致。

## 12. What NOT to Copy

### 12.1 只适合 Lore 网站的内容

- 占据大部分首屏、只提供氛围而几乎不提供信息的 Hero；
- “Scroll to Begin”式长篇揭幕和强制阅读节奏；
- 地图镜头、环境音、地标动画等世界探索机制；
- 大量居中长文、章节化入场和沉浸式页面转场；
- 把每个页面都当作独立专题站进行主题化。

这些机制适合低频、主动沉浸的 Lore 消费；LeagueNews 的核心任务是高频确认“有什么新事、是否重要、是否可信、有哪些进展”。

### 12.2 会降低新闻网站信息密度的做法

- 每条内容都使用大图和超大留白；
- 普通列表依赖横向 Carousel 隐藏大量内容；
- 元数据为了氛围被过度弱化；
- 标题全部大写、过宽字距或大号 Display；
- 多数内容需要 Hover 才出现动作或说明；
- 用多段入场动画延迟内容出现；
- 为所有页面保留 60–80vh 的 Hero。

### 12.3 依赖 Riot 专属美术资产的部分

- 官方角色 Splash Art、地区环境图、徽记与地图；
- Beaufort for LOL、Spiegel 等 Riot/League 品牌字体；
- 地区材质、图腾、武器、建筑语言和专属装饰框；
- 官方专题 Key Art、动态图像、环境音与 Cinematic；
- 角色/地区配色的既有玩家认知。

这些资产不能被视为通用设计系统资源，也不能通过近似重画来规避其专属性。

### 12.4 直接照搬会显得廉价的部分

- 每个框都使用暗金描边、切角和角饰；
- 以免费“奇幻 Serif”替代字体策略，并用于所有文字；
- 在低质量或来源混杂的图片上统一加重黑金滤镜；
- 使用假徽记、盾牌、剑、龙纹作为无语义图标；
- 按钮持续发光，卡片 Hover 大幅上浮，背景添加粒子；
- 把可信度、重要性、热度包装成 RPG 属性面板；
- 为了“游戏感”牺牲中文可读性和移动端密度。

### 12.5 版权与品牌模仿风险

- 不复制 League/Universe 标志、地区徽记、地图、角色画面、边框纹样或专属图标；
- 不未经许可打包或自托管 Riot 字体；
- 不复刻 Universe 的特定页面构图到足以造成官方站点混淆；
- 不使用“看起来像 Riot 官方发布”的视觉伪装非官方来源；
- 不把研究所得颜色值当作应原样复制的品牌色板；
- 对来源媒体保留清晰出处与权利边界，不能因统一视觉处理而抹去来源身份。

学习对象应是“图像如何与信息融合、层级如何建立、装饰如何节制、关系如何呈现”，而不是 Riot 可识别资产的近似复刻。

## 13. Transferable Design Principles

以下原则可用于后续 LeagueNews 设计阶段，但本文件不定义具体页面或组件：

1. **把产品设计成编辑出版物，而不是监控面板。** 技术处理链是可信基础，不应成为公开页面的第一视觉主题。
2. **一个视图只设一个第一注意点。** 用位置、尺度、留白和对比共同建立，不依赖醒目 Badge。
3. **先建立内容语境，再展示内容数量。** 栏目命题、时间范围和阅读目的优先于统计数字。
4. **建立 Display / UI / Reading 三角色排版。** 让品牌语气集中在入口，让扫描与长读保持清晰。
5. **采用有色温的暗部层级，而不是纯黑卡片墙。** Canvas、Surface、Hover、Scrim 各司其职，差异克制但可辨。
6. **把暖白用于内容，把金属色用于结构与归属。** 金色是稀缺标点，不是默认文字色或万能状态色。
7. **Featured 是编辑构图，不是样式开关。** 必须同时改变位置、面积、上下文和内容节制程度。
8. **图片先服务辨识与语境，再服务装饰。** 建立统一的裁剪与明度范围；缺图内容仍须保持完整层级。
9. **同类内容稳定，异级内容有意破格。** 普通列表利于比较，Feature 才获得不同的图文关系。
10. **用低对比线、菱形或短标签标记结构转折。** 每个 Section 只保留一个主要装饰动机，并让它具有语义。
11. **以空间而非容器数量组织页面。** Section 间距明显大于卡片间距，减少层层嵌套与面板堆叠。
12. **让消息、事件、日报拥有不同的信息重心。** 发布、持续进展和每日策展不是同一种内容，只共享底层事实与可信关系。
13. **把来源与证据设计成可追溯层，而不是视觉噪声。** 快速浏览展示必要信任线索，详情再交付完整证据。
14. **动效只服务反馈、定位和真实状态变化。** 高频浏览中避免自动轮播、强制揭幕、持续环境动效和逐卡入场。
15. **品牌感来自重复的决策规则，而不是重复的品牌符号。** 即使没有 Riot 插画和字体，层级、节奏、关系、克制和图像处理也应仍然成立。

## Research Notes & Sources

本研究采用以下证据层级：

1. **Universe 官方线上页面与生产样式**：首页、地区、英雄、故事与漫画页面；用于核对实际字体角色、颜色层次、断点、宽度、动效时长、图像 Overlay 和装饰结构。
2. **Universe 页面截图样本**：用于比对首页 Featured、地区索引、英雄详情、漫画 Hub 的真实构图与信息权重。
3. **Riot 设计人员公开复盘**：用于验证设计意图、内容发现问题、上下文连接和响应式策略，而不是仅凭截图猜测。
4. **LeagueNews 当前产品文档与公开前端结构（只读）**：用于确认消息、事件、日报、信源、重要性/可信度/热度等信息类型，从而界定哪些原则可迁移；未据此提出下一阶段改造方案。

### 研究限制

研究期间，Universe 官方站在受控浏览器中出现连接被远端关闭/长时间加载的情况；官方 HTML、分页面样式与媒体资源可直接读取。因此本文以官方生产 CSS 和页面元数据为定量依据，以公开页面截图和 Riot 设计人员复盘为视觉与意图交叉验证。对无法稳定实测的逐帧交互，本文只记录从生产样式可确认的行为，不对滚动手感、设备性能或当前线上所有专题页状态作过度推断。
