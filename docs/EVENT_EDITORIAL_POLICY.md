# 事件编辑规则 v1

事件是一个可以被证据验证的现实状态变化，不是相似消息的文件夹。事件准入、重要性和
可信度相互独立：低重要性的普通 LPL 常规赛结果仍可形成事件；低可信度的单源转会爆料
也可立即形成未确认事件。

## 事件准入

- 普通 LPL 常规赛按中国时区比赛日形成 `match` 事件，稳定键为
  `matchday:lpl:YYYY-MM-DD`。同一天的赛程预告、进行中、赛果和赛后内容属于同一事件。
  普通常规赛重要性通常为 `0.50-0.58`；只有明确影响排名、晋级或淘汰时才提高。
- 季后赛后程的半决赛、胜者组决赛、败者组决赛和总决赛，在能够确定对阵双方时可按单场
  系列赛形成事件。`scheduled -> live -> completed` 是生命周期变化，不是拆分事件的依据。
- 明确包含选手或教练、转会动作和目标战队的单源爆料形成 `transfer` 事件，初始
  `lifecycle_status=unconfirmed`。模糊的“大动作”暗示不形成事件。
- 版本预览、完整预览、上线和热修复优先进入同一个 `patch` 主事件。
- 新英雄、英雄重做和核心玩法系统可形成 `major_gameplay_change` 事件。当前审核工作流
  仍为每条消息选择一个主事件；一条消息作为多个事件证据将在一对多审核决策中实现。
- 互动、二创、泛宣传、纯观点和没有新事实的重复转载不创建新事件。

事件身份优先于时间窗口。游戏模式使用规范实体生成稳定键，例如
`mode:classic-mode`；“新模式”“游戏模式”“玩法模式”归一为同一分类。重大玩法和
游戏模式候选使用 180 天窗口，并以绝对发布时间差判断，因此离线批量数据按正序或倒序
处理都应命中同一事件。

候选检索采用两阶段召回：

- `strong`：稳定键、RawItem 版本链、核心实体或标题明确命中。
- `broad`：没有精确身份信号，但处于该事件类型的合理时间范围内。宽候选携带事件标题、
  摘要和核心实体，交由事件编辑判断别名、缩写、旧译名、父子对象和附属内容关系。

单条分析遇到礼包、皮肤、图标、封面、奖励、截图和测试服资源等附属对象时，必须同时
提取文本明确指向的父级模式、英雄、赛事、版本或活动。候选存在时如果仍选择 `create`，
必须通过 `candidate_rejections` 逐一说明为何每个候选都不是同一事件，否则草稿校验失败
并自动重试。附属素材没有改变核心事件状态时使用 `context`，不增加 revision。

### 国服神话商城轮换

- 国服神话商城的每周轮换形成一个低重要性 `activity` 小事件，稳定键按中国时区 ISO 周
  生成，例如 `mythic-shop:cn:2026-w30`。
- 同一周的每日轮换加入该周事件，使用 `update_kind=context`，不增加 revision。
- 无论成员消息自身的重要性多高，事件重要性保持在 `0.30-0.45`，成员分数不再反向覆盖
  事件级编辑分数。
- 百度贴吧、微博和腾讯国服来源默认视为国服；文本明确写明国服也可判为国服。
- X/Twitter 来源的神话商城轮换按国际服处理，不得加入国服周事件，也不单独进入本站的
  事件层，使用 `not_event`。
- 周消息与每日消息无论处理顺序如何，都使用同一个周稳定键。标题中的“每周/每日”优先
  于正文中的附带描述判断轮换节奏。

## 事件更新

`update_kind` 区分：

- `new_fact`、`confirmation`、`refutation`、`correction`：构成显著更新并增加 revision。
- `context`、`duplicate_evidence`：可以补充证据和改变可信度，但不增加 revision，也不
  改写最新进展。

证据使用 `supports`、`contradicts`、`context` 三种立场。

### 同一来源文档的版本链

`RawItem.supersedes_raw_item_id` 表示同一来源文档的新采集版本，不表示新的消息或独立
来源：

- 消息列表和事件处理台只展示版本链中没有 successor 的最新版本。
- 已被取代的 NormalizedItem 不允许启动或批准事件聚合。
- 新版替代已经属于事件的旧版时，原位替换 `event_messages` 成员，不追加第二条证据。
- 页面修订没有实质新事实时使用 `duplicate_evidence`，不增加事件 revision；确有新增
  事实时才生成新的事件 revision。
- 旧 RawItem 和旧 NormalizedItem 保留用于审计，不从数据库删除。

## 可信度

证据先按 `independence_key` 去重。v1 默认使用 `source:{source_id}`；同一账号的多条
消息不会重复增加可信度。

非官方支持证据的有效强度上限为 `0.85`：

```text
positive = 1 - product(1 - supporting_strength)
negative = 1 - product(1 - contradicting_strength)
credibility = positive * (1 - negative)
```

只有原始官方来源直接确认其权责范围内的核心事实，并经事件审核确认后，
`is_official_confirmation` 才为真。官方转发不算直接确认。官方支持将事件标为
`official_confirmed` 且可信度为 `1.0`；官方否认将核心主张标为 `officially_refuted`。

## 重要性

事件重要性不累加成员消息数量，也不因官方身份加分。v1 使用成员消息重要性的最高值
作为稳定基线，事件审核可以提供事件级分数和依据。后续应将影响范围、改变幅度、持续
时间、行动价值和用户相关性保存为独立评分维度。

公开卡片展示事件类型、生命周期、重要性、可信状态、独立来源数、证据数和最新进展；
内部 `event_key` 与 revision 历史保留在详情审计区。
