# 消息分类规则

> 状态：当前运行规则
>
> 存储版本：`message-taxonomy-v2`
>
> 设计版本：Products v0.6 / Content Form v0.4 / Message Type v0.9 / Topics v0.2
>
> 本文是消息处理阶段的工作规则，不描述事件状态、事件聚合或消息可信度。

## Products

`products` 描述一条消息实际涉及的产品或业务域。字段允许多选，但默认应当单选，只有消息实质性讨论多个产品时才增加标签，最多选择 3 个。判断依据是消息内容，不是发布账号。

分类输入默认已经通过相关性筛选，因此 `unknown` 不表示“无关消息”，只表示现有内容不足以判断产品。它主要承接纯媒体、纯链接或其他缺少可读语义的消息。

| code | 名称 | 主要内容 |
| --- | --- | --- |
| `lol_pc` | 英雄联盟 PC | 《英雄联盟》PC 端游戏本体、客户端、版本改动、英雄、装备、符文、玩法、模式、皮肤、商城和游戏内活动。也包括开发者报告、开发日志或路线图中针对端游的未来改动、模式和开发进展。 |
| `tft` | 云顶之弈 | 云顶之弈（TFT）的赛季、套装、棋子、羁绊、强化符文、玩法、模式、外观、商城和活动。 |
| `lol_esports` | 英雄联盟电竞 | 英雄联盟职业赛事及其生态，包括联赛、赛程、比赛、战队、选手、转会、赛事规则、转播和现场活动。 |
| `lol_universe` | 英雄联盟宇宙 | 符文之地世界观、角色故事、背景设定、叙事内容，以及以该宇宙为核心的动画、影视、音乐或其他创意作品。 |
| `other_lol_product` | 其他英雄联盟相关产品 | 与 League of Legends IP 直接相关、但不属于以上四项的产品，例如英雄联盟手游、符文之地传说、2XKO、Riftbound（裂界征伐）等。具体产品名作为内容中的实体或辅助上下文，不拆成新的主产品。 |
| `riot_ecosystem` | Riot 生态与关联业务 | Riot 公司级事务、招聘与合作、面向第三方开发者的开放平台或 API、Riot 账户与跨产品基础设施，以及 Riot 周边、收藏品、音乐、视频、授权媒体和其他平台的业务消息。 |
| `unknown` | 产品未知 | 原始内容不足以判断产品，例如只有无法理解的图片、视频或链接。它是证据不足的兜底值，不用于已确认的无关消息。 |

### 边界规则

- 产品根据消息讨论的对象判断，不根据文章名称、作者职位或发布账号判断。
- 文本明确出现具体产品名时，以该产品作为讨论对象；该产品复用的英雄、皮肤或世界观元素不能单独把产品改判为 `lol_pc` 或 `lol_universe`。
- 《开发者报告》、开发日志和路线图不是独立产品。正文讲 LoL 端游未来改动、模式或开发进展时标注 `lol_pc`；标题或作者出现“开发者”不能触发 `riot_ecosystem`。
- 聊的是游戏内内容，标注对应游戏产品；不能因为来源是 Riot 官方就标注 `riot_ecosystem`。
- 聊的是职业比赛或职业生态，标注 `lol_esports`；若同时明确讨论游戏版本或玩法，可再标注 `lol_pc` 或 `tft`。
- 世界观、角色叙事是消息主体时标注 `lol_universe`；普通皮肤、商城素材或游戏内资产仍归对应游戏产品。
- 其他英雄联盟相关产品使用 `other_lol_product`；不为低频产品单独扩展枚举。
- `riot_ecosystem` 是合并后的业务域，只在消息主体是公司级事务、开放平台、账户或跨产品基础设施、游戏外商业内容或其他平台业务时命中。它不等同于“所有 Riot 发布的消息”。
- 优先选择 1 个最主要的产品；仅顺带提及、作为例子出现或只存在于背景中的产品不增加标签。
- 消息确实有多个并列主体时可选择 2～3 个产品；即使涉及更多产品，也只保留与核心主张关系最强的 3 个。
- `unknown` 与其他产品互斥；使用时固定为 `products=[unknown]`，不能同时附加猜测出的产品。
- `products` 数组的顺序固定为本文表格顺序，顺序不表达优先级。

### 当前约定

分类规则只定义当前产品范围和边界，不回写 RawItem，也不静默改写既有 NormalizedItem。
回归评测必须记录 `classification_version`，并单独覆盖 `other_lol_product` 与
`riot_ecosystem` 的边界案例。

## Content Form

`content_form` 描述消息承载内容的形式，单选且必须有值，仍由 LLM 根据完整输入判断。它不作为调用 LLM 前的门禁，也不能代替 `products`、`message_type` 或 `topics`。

| code | 含义 | 下游处理规则 |
| --- | --- | --- |
| `original` | 发布者直接发布的原创消息，正文或标题包含可处理的语义内容。 | 正常完成分类和重要性计算。 |
| `repost` | 转发或重新发布他人的消息，自身没有实质性新增内容。 | 继续处理；重要性档案分确定后扣 8 分，排序阶段不重复扣分。 |
| `quote` | 发布者引用另一条消息，并附加自己的文字、判断或补充信息。 | 正常完成分类和重要性计算，同时保留引用关系。 |
| `media_only` | 标题与正文都没有足够可读语义，只有图片、视频或其他媒体。标题是当前消息证据；若仅根据标题就能忠实概括消息的对象与事项、生成非空摘要，则已有可处理语义，不属于仅媒体。 | LLM 仍返回该内容形式，同时令其他语义分类全部为 `unknown`；不执行重要性模型，分数写为 0。 |
| `link_only` | 只有链接或嵌入地址，没有成功提取到可读正文。 | LLM 仍返回该内容形式，同时令其他语义分类全部为 `unknown`；不执行重要性模型，分数写为 0。 |

### 处理顺序

1. 采集并保存 RawItem。
2. 相关性筛选和必要翻译完成后，内容分析调用同时判断 `products`、`content_form`，并提取标题、摘要和实体；该调用不接收消息类型或主题候选。
3. 若 `content_form` 为 `media_only` 或 `link_only`，统一补全 `products=[unknown]`、`message_type=unknown`、`topics=[unknown]`，摘要和实体留空。
4. 得到上述结果后跳过分类与重要性模型，以 0 分发布消息处理结果。
5. `original`、`repost` 和 `quote` 进入下一次调用；运行时依据已批准的产品和信源披露消息类型、主题候选，并在同一次响应中提取重要性特征。

### 边界规则

- 是否为 `repost` 或 `quote`，根据消息结构和发布者是否增加了实质内容判断，不能只凭正文中出现转发符号或链接判断。
- 引用内容但没有任何新增语义时使用 `repost`；存在可独立理解的新增文字时使用 `quote`。
- 链接目标的正文已经被连接器成功提取时，不使用 `link_only`，应根据提取后的完整内容重新判断形式。
- 标题与正文同属当前消息证据，不能因为正文只有图片就忽略明确标题。若仅根据标题就能忠实概括消息的对象与事项、生成非空摘要，应使用 `original`；只有标题和正文都无法提供可处理语义时才使用 `media_only`。
- 当前系统没有通用图片或视频理解能力，因此不能根据媒体内容猜测产品、类型、主题或重要性；未来即使接入多模态模型，也仍由 LLM 产出内容形式和语义分类，不把内容形式写成模型调用前的固定门禁。

## Message Type

`message_type` 描述一条消息作为发布内容的主要性质，单选且必须有值。运行时先由内容分析调用确定 `products` 和 `content_form`；随后根据已批准的 `products` 与信源性质生成候选子集，在分类与重要性调用中选择 `message_type`。

这里的“官方信源”指 Riot、英雄联盟或赛事主办方等官方发布渠道；“非官方信源”指社区账号、媒体、爆料账号和其他第三方渠道。信源用于收缩候选集合，不直接替代内容判断。

### 渐进式披露选择规则

内容分析调用先确定 `products`。分类与重要性调用只接收信源条件相符、且“适用 products”与已选产品至少有一项相交的候选。例如消息同时属于 `lol_pc` 和 `lol_esports` 且信源为官方时，候选是两组官方类型的并集，但最终仍只能输出一个消息类型。`unknown` 始终作为兜底候选。

### 共通约束

- `game_patch_notes`、`game_official_preview`、`game_announcement`、`game_notice`、`game_promotion_interaction` 只能从游戏官方信源表中暴露。
- `game_leak`、`game_community_notice`、`game_community_promotion_interaction`、`game_community_discussion`、`esports_rumor_speculation`、`esports_community_discussion` 只能从非官方信源表中暴露。
- `esports_announcement` 和 `esports_promotion_interaction` 只用于 `lol_esports`；赛事相关内容不能因为提到某个英雄就改成普通游戏类型。
- `game_official_preview` 与 `game_promotion_interaction` 的边界先看发布目的和信息密度：多项具体机制、数值、规则、玩法或开发说明才支持官方预览；短帖、视频、口号式展示、预热和参与引导属于推广互动。上线日期、测试服或“以正式服为准”只说明信息阶段，不能单独支持官方预览。
- `game_announcement` 与 `game_promotion_interaction` 的边界先看主要传播目的：游戏公告以可独立核验的明确时间、范围、参与或获取方式、规则和安排等正式事实为主体，宣传措辞只是辅助；推广互动以展示、造势、唤起回忆或参与引导为主体。上线、现已上线、即将上线、回归等状态不能单独支持游戏公告；正式事实只是宣传背景、没有形成独立完整告知时，仍属于推广互动。
- 如果 `content_form` 是 `media_only` 或 `link_only`，`message_type` 固定输出 `unknown`，不再从上述候选中猜测。
- `unknown` 是单选兜底，不与其他 `message_type` 并列；调整产品与信源候选矩阵时必须同步修改运行时目录和测试。

## Topics

`topics` 描述消息实际讲到的内容领域，允许多选。主题候选只依赖已批准的 `products`，不依赖官方或非官方信源；运行时只披露适用于至少一个已选产品的主题候选。

主题只标注消息的实质内容，不标注文档形式、发布阶段、可信度、事件状态或具体实体。当前不设置
数量上限，但必须忽略顺带提及；`unknown` 与其他主题互斥，使用时固定为 `topics=[unknown]`。

### 主题选择规则

1. `products` 在前一个内容分析调用中确定；分类与重要性调用只接收适用于已选产品的主题候选并判断 `topics`。
2. 每个选中的主题必须至少适用于一个已选中的产品。多产品消息可以从这些产品所适用主题的并集中选择。
3. 主题允许多选，但只选择消息实质讨论的主题，不因顺带提及某个对象而增加主题。
4. `unknown` 与其他主题互斥；选择 `unknown` 时固定输出 `topics=[unknown]`。
5. 当 `content_form` 为 `media_only` 或 `link_only` 时，不根据缺失的正文推测主题，固定输出 `topics=[unknown]`。
